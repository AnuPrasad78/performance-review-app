# Deployment and database versioning — Azure Container Apps

How the portal runs on Azure, how a release ships, and how to roll back the
code, the schema, or the data. Everything runs from a terminal with the Azure
CLI, and needs only **Contributor** on the subscription:

| Path | Purpose |
|---|---|
| `deploy/<env>.env` | Per-environment resource names, scale and **non-secret** settings. Committed. Only `dev` exists today. |
| `scripts/azure/setup.sh <env>` | Creates whatever is missing; re-run any time to apply config changes. Idempotent. |
| `scripts/azure/deploy.sh <env>` | Releases the current commit: build → migrate → roll → readiness check. `--tag <sha>` rolls back. |
| `scripts/azure/run-job.sh <env> migrate\|downgrade <rev>` | Runs the migration job by hand and waits. |
| `scripts/azure/lib.sh` | Shared helpers (config loading, Key Vault refs, image build, job runner, probes). |

CI (`.github/workflows/ci.yml`) tests the code, the migrations and the images,
and lints these scripts. It does not deploy.

## Why no role assignments

The scripts never create an Azure role assignment, because Contributor cannot:

- **Key Vault** uses *access policies*, not RBAC. The app identity gets
  get/list on secrets; whoever runs setup gets get/list/set/delete.
- **Images** are pulled with the registry's *admin credentials*, stored as a
  Container Apps secret, not with an AcrPull role.
- **Deploys** run from your terminal after `az login`, not from a GitHub
  pipeline, which would need an app registration with a federated credential.

## Topology

```
 terminal ── deploy.sh ──▶ az acr build (in Azure) ──▶ registry: performance-review-{api,web}:<git-sha>

internet ─HTTPS─▶ web  (nginx: SPA + /api proxy)        external ingress, the only public endpoint
                   │  private network inside the Container Apps environment
                   ▼
                  api  (FastAPI, uvicorn)                internal ingress only
                   │
                   ▼
           PostgreSQL Flexible Server                    dev: public endpoint, Azure-only firewall
                   ▲                                     PRIVATE_NETWORK=true: VNet, no public endpoint
       migrate job (same image as api: `alembic upgrade head`)
```

- **Same origin.** The browser only talks to `web`; nginx forwards `/api/*` to
  `api`. There is no CORS, and the front-end image does not bake in an API URL.
- **One image, two roles.** The api app and the migration job run the same
  image, so the code that migrates the schema is the code that serves it.
- **Secrets** live in Key Vault and reach the api through Key Vault references
  read by a user-assigned managed identity:
  - `database-url`: generated by setup with the Postgres password. It uses
    `?ssl=verify-full`, so the server certificate is checked against the
    image's CA bundle.
  - `session-secret`: generated once. It signs the session cookie, so changing
    it signs everyone out.
  - `entra-client-secret`: prompted for once, only when SSO is configured.
  - `provision-password`: generated once (or taken from
    `KV_SEED_PROVISION_PASSWORD`), only with `PASSWORD_SIGN_IN=true`. It is the
    shared password of the email form, the same scheme as the Apex portal.
- **Sign-in.**
  - With `ENTRA_CLIENT_ID` set, the browser goes to `/api/auth/sso/login`.
    Microsoft redirects back to `https://<web host>/api/auth/sso/callback`,
    and the api sets the session cookie.
  - Setup prints that redirect URI. It must be listed on the app registration
    (*Authentication → Web → Redirect URIs*).
  - `PASSWORD_SIGN_IN=true` makes the email form check `provision-password`:
    every roster employee and `ADMIN_EMAILS` address signs in with it, and a
    correct pair sets the same session cookie as SSO. Read it with
    `az keyvault secret show --vault-name <kv> -n provision-password --query value -o tsv`.
    To rotate it, set a new value there and restart the api revision.
  - Without it, `APP_ENVIRONMENT=dev` keeps the email-only sign-in. It trusts
    any roster address typed, so use it for test data only. In `prod` the
    form is closed and SSO is the only way in.
  - `prod` requires SSO, and setup refuses to configure prod without it.
- **Probes.** setup adds them once through ARM, because `az` has no probe
  flags.
  - api liveness `/api/health`: never touches the database, so a database
    outage takes replicas out of rotation instead of restart-looping them.
  - api readiness `/api/ready`: the database is reachable *and* its schema is
    not behind this image.
  - web: `/healthz`, answered by nginx itself.

## Sizing

The data is small: one evaluation row per employee per year, tens of MB. For
~2,000 employees, load peaks near the submission deadline and is mostly
autosave PATCHes of a few indexed single-row queries.

**Connection limit.** The most connections the API can open is
replicas × `API_WORKERS` × (`PR_DB_POOL_SIZE` + `PR_DB_MAX_OVERFLOW`), and it
must stay below the server's `max_connections`.

| | Calculation | Connections | Server limit |
|---|---|---|---|
| dev | 1 × 2 × (5 + 5) | 20 | B1ms allows about 50 |
| prod sizing | up to 4 replicas | about 80 | B2s allows several hundred |

Dev scales both apps to zero when idle, so the first request after a quiet
spell takes a few seconds. For production, use:

- `PRIVATE_NETWORK=true` and minimum replicas of 1;
- Postgres B2s with longer backup retention;
- `GeneralPurpose` with high availability if a database failover must be
  seamless.

## First-time setup of an environment

Prerequisites:

- Azure CLI in WSL: `az login`, then `az extension add --name containerapp --upgrade`.
- **Contributor** on the subscription. setup creates the resource group and
  registers resource providers.

Steps, shown for `dev`:

1. **Check `deploy/dev.env`.** The globally unique names (`ACR_NAME`,
   `KEY_VAULT_NAME`, `POSTGRES_SERVER_NAME`), `ADMIN_EMAILS` and, for SSO,
   `ENTRA_CLIENT_ID`. Commit any change.
2. **Create the resources.** A first run takes ~15–20 minutes, mostly
   Postgres. It ends by printing the URL and, with SSO, the redirect URI.
   ```bash
   ./scripts/azure/setup.sh dev
   ```
3. **Release.** On an empty database the migration job builds the whole
   schema from revision A0.
   ```bash
   ./scripts/azure/deploy.sh dev
   ```
4. **Register the redirect URI.** With SSO on, add the printed redirect URI
   to the app registration.

If `az acr build` fails with `TasksOperationsNotAllowed` (some subscriptions
block ACR Tasks), set `BUILD_MODE=docker` in the env file to build locally
and push.

### Moving the existing database across

The current database already carries every legacy table and is stamped with a
revision after A1. Revision A0 is an ancestor of that revision, so nothing
re-runs and no `alembic stamp` is needed; the next release's migration job
applies whatever revisions it is missing.

1. `pg_dump --format=custom --no-owner --no-privileges` from the old server.
   `alembic_version` travels with the data.
2. `pg_restore --no-owner --role=<admin> --dbname=performance_review` into the
   new server.
   - **dev:** add a firewall rule for your own IP for the duration, then
     remove it.
   - **private network:** run the restore from a one-off Container Apps job
     inside the VNet.
3. Run `alembic check` against it. It must report *No new upgrade operations
   detected* before you send any traffic. The check is read-only and compares
   the live schema to what the code's models expect:
   ```bash
   PR_DATABASE_URL='postgresql+asyncpg://…?ssl=require' alembic check
   ```

## Releasing

```bash
git checkout <branch> && git pull     # deploy committed, pushed code
./scripts/azure/deploy.sh dev
```

The script stops at the first failure:

1. **Checks.** It refuses a dirty working tree, or a branch other than
   `DEPLOY_BRANCH` when that is set. It warns if the commit is not pushed.
2. **Build.** `az acr build` builds both images, tagged with the 12-character
   commit SHA. An existing tag is reused.
3. **Migrate.** It points the migration job at the new api image, starts it
   and waits.
   - A failed migration has already rolled back its own transaction: the
     schema and `alembic_version` are untouched.
   - The job goes back to its previous image and the apps are **not** rolled.
   - Read the job's console logs, fix forward, and release again.
4. **Roll.** api first, then web, so the new SPA never talks to the old api.
   A new api revision takes traffic only once `/api/ready` passes.
5. **Check.** `https://<web host>/api/ready` must answer through the public
   proxy. The script then prints the rollback command.

**Why migrations are a job, not a container start-up step.** With several
replicas, each would race to migrate, and a failed migration would crash-loop
the app instead of failing the release. The migration runtime still takes a
Postgres advisory lock, so two overlapping runs serialize: the second finds
the schema at head and does nothing.

**Reviewing the SQL before a release.** This renders exactly what will run,
without touching the database:

```bash
alembic upgrade <current_revision>:head --sql
```

The current revision is in `/api/ready`'s `schemaRevision`.

## Rolling back

Decide which layer is broken, and roll back the narrowest one.

### 1. Code only (the common case)

```bash
./scripts/azure/deploy.sh dev --tag <previous-sha>
```

The previous SHA is printed by every release.

- The apps go back to that tag's images, which are already in the registry.
  Nothing is built and no migration runs.
- An older image cannot migrate a newer schema: it does not know the newer
  revision, so `alembic upgrade head` would fail.
- The older code runs fine on the newer schema because migrations are
  expand-then-contract (rules below), and `/api/ready` deliberately stays
  green when the schema is *ahead* of the code.
- The migration job stays on the newer image, which is the one holding the
  downgrade code.

### 2. Schema

Only do this when a migration itself is wrong, and only **after** step 1:

```bash
./scripts/azure/run-job.sh dev downgrade <previous_revision>
```

- It asks you to type the environment name.
- It runs `alembic downgrade` once on the job's current (newer) image, then
  restores the job's `upgrade head` arguments.
- The run is transactional and holds the advisory lock, exactly like an
  upgrade.
- Every downgrade in the chain is exercised by CI's stairway test, so a
  merged migration's rollback is known to run.
- It refuses `base` and A0: A0's downgrade drops every table and exists only
  for CI round trips.

**Downgrades that lose data.** Some downgrades cannot restore what their
upgrade changed. A3's downgrade, for example, drops the text `org` values.
When a downgrade would destroy data, use step 3 instead.

### 3. Data

When data itself is damaged (a bad roster import, a destructive migration),
use **point-in-time restore**. Backups are kept for `POSTGRES_BACKUP_DAYS`.

1. Restore to a new server. The current one stays untouched:
   ```bash
   az postgres flexible-server restore --source-server <server> --name <new-server> --restore-time <UTC time before the damage>
   ```
2. Verify the restored data, then point the `database-url` secret at the new
   server:
   ```bash
   az keyvault secret set --vault-name <kv> -n database-url --value '...'
   ```
3. Restart the api revision (below) so it reads the new value.

## Operations

| Task | How |
|---|---|
| Live logs | `az containerapp logs show -n <api or web app> -g <rg> --follow` |
| Migration history | `az containerapp job execution list -n <migrate job> -g <rg> -o table` |
| Schema revision | `curl https://<web host>/api/ready` → `schemaRevision` / `codeRevision` |
| Change a setting or scale | edit `deploy/<env>.env`, run `setup.sh <env>` |
| Rotate a secret | `az keyvault secret set --vault-name <kv> -n <name> --value ...`, then `az containerapp revision restart -n <api app> -g <rg> --revision $(az containerapp show -n <api app> -g <rg> --query properties.latestRevisionName -o tsv)` |
| Save dev cost | `az postgres flexible-server stop -g <rg> -n <pg>` (auto-starts after 7 days) |

Container Apps re-reads Key Vault references about every 30 minutes, but a
running container only sees new values after a restart. Track the Entra
client secret's expiry (24 months at most).

## Writing migrations (rules CI enforces or relies on)

- **One logical change per migration.** Never edit a migration after it has
  been applied anywhere. The one exception so far: A2's downgrade ran its
  cleanup query after dropping the column the query reads, so it could never
  succeed anywhere. It was fixed in place because no database could have
  applied it.
- **Expand, then contract.** A release may only *add* things the previous
  release's code ignores: nullable columns, new tables, new indexes. Removing
  or renaming something the previous code reads happens one release *later*,
  after no running code reads it. This is what keeps code-only rollback safe.
- **Every migration has a working `downgrade()`.** CI's stairway test runs
  upgrade → downgrade → upgrade on every revision, then a full head → base →
  head round trip, then checks that review data survives a one-step rollback.
  Document any downgrade that cannot preserve data, as A3 does.
- **The models match the schema.** CI runs `alembic check` on a database
  built from nothing. A model change without a migration, or the reverse,
  fails the build.
- **Keep migrations reviewable and safe to run on a live database:**
  - Revision ids are at most 32 characters (the width of `alembic_version`).
  - Migrations after A2 must render offline (`--sql`).
  - DDL waits at most 10 s for a table lock (`lock_timeout` in
    `alembic/env.py`). A migration that cannot get its lock fails cleanly
    instead of stalling live requests.
  - Build indexes on large tables with `CREATE INDEX CONCURRENTLY` in their
    own non-transactional migration.

## Known gaps

- **Only `dev` exists.** A prod environment is a new `deploy/prod.env`:
  - `PRIVATE_NETWORK=true`;
  - `APP_ENVIRONMENT=prod` with SSO configured;
  - minimum replicas of 1, B2s, and longer backups;
  - `KV_PURGE_PROTECTION=true`.
- **Audit history.** Ratings and feedback still have none; CLAUDE.md requires
  them to be versioned.
- **Custom domain.** The public address is the Container Apps default domain.
  Setting `CUSTOM_HOSTNAME` changes the SSO redirect URI: update the Entra
  registration in the same change.
